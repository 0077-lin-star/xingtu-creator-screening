# 批量采集记录与时间分配

默认目标是基本匹配候选明细，最终复核由用户完成。每次运行在用户指定的可写目录创建独立结果文件；未指定时使用当前工作区的output目录。项目资料与运行结果应保存在公开Skill仓库之外。

## 轻量记录

用一个JSON或结构等价文件即可，不为初筛建立复杂打分/终审系统。

| 部分 | 必要记录 |
| --- | --- |
| 任务 | 项目、brief来源、初筛/明确要求的严格模式、目标数量、时限、开始/结束时间 |
| 条件 | 基本方向、明确不可放宽项、加分项；原文与用户修正 |
| 搜索 | 入口、实际关键词/筛选、分页位置、发现ID、排除原因 |
| 候选 | 平台ID类型与完整ID、昵称、主页、初筛保留原因、待用户复核点、原名单行 |
| 资料 | 指标原文/标准值/单位/窗口/规格/流量状态、来源时间 |
| 图像 | 平台ID、四种类型、粉丝/观众来源、采集状态、文件路径、Excel目标格及导出核对状态；缺失需记失败步骤 |
| 联系 | 菜单“查看微信”和展开简介两路分别记录操作状态、原文、类型、达人/机构归属、来源时间与结果；写入状态另记 |
| 队列 | 已初看、待采集、已成表、资料缺口、恢复位置 |

以平台ID关联，避免昵称重名/改名串图。每完成一账号或小批写入文件；不重复浏览已完成账号。

使用 [联系与截图操作流程](contact-and-screenshot-workflow.md) 中的字段映射和补采队列。已保存图不等于已入表，看到联系按钮不等于已读取微信。旧批次字段名不一致时先归一化再导出；不能让缺键、路径错误、导航失败都变成“平台未展示”。连续同类失败先修采集步骤，已找到足量候选后优先补齐资料。

## 两阶段衔接

1. 多路发现并快速初看，排除严重不符，基本匹配者进入采集队列；记录未初看的线索但不计交付候选。
2. 分批完成候选的全部可采集字段、四图、公开联系信息。列表直接可得的数据可随发现保存，不必为每个字段重新导航。
3. 截图与联系采集覆盖整个保留队列，不只覆盖“最推荐”或“数字全达标”的前几行。其他候选即使有复核点也同样采集。
4. 一批持续出现同类严重不符时改词/入口；价格带和销量不满足不是收窄入口的理由。
5. 给用户的明细只放基本匹配账号，严重不符内部记录即可。用户明确要求全量名单明细时按其范围保留，不能自动省略。

## 数量口径

- 初筛候选数：已初看、基本匹配且写入明细的唯一账号，包含有待用户复核事项者；不是最终通过数。
- 四图齐全数：真正取得并嵌入四张对应局部图的账号数。
- 联系取得数：取得真实公开达人/机构商务联系信息的账号数，分清归属；不是只有微信才算联系信息。
- 采集已处理：字段有数据或真实缺失原因；仍缺资料不称齐全。用户手填结算价不算漏采。
- 未初看、未写入明细、重复ID、严重不符及公司不混入达人交付数。未完成队列单独报告。

不默认报告严格通过率，也不以提高该比例减少候选。缺口按用户本次初筛目标计算。

## 时间与执行重点

本次数量/时限优先；无指定则目标200个基本匹配候选、60分钟总时限。目标口径已由用户改为初筛量，不再追求200个终审通过者。不能保证平台一定能提供该数量。

使用同一带时区时间戳记录开始、采集结束、成表完成。总时限包括采集、Excel与交付检查。未单独记录阶段耗时就写未单独计时，不倒推。

把主要时间给多路发现、批量初看和逐行资料采集。默认不做逐条完整审片、完整结局审查、全账号历史商业复盘、复杂评分或无休止的制作证据追查。基本方向有线索且没有已知严重不符就可以先交用户。

根据首批实际速度估计数量和资料补齐成本；预留成表时间，及时报告瓶颈。若候选不足，优先解除误设的价格/销量过滤，扩展同义词、其他人设路径、分类和相关机构入口，不用重复深审已找到的几个账号填满一小时。

发现更多候选不意味着可以不采图：按小批完整处理，平衡剩余时间。首批真实数据确认嵌图格式后复用。到时限交付实际明细、数量缺口和未完成字段，不默默加时或声称齐全。达到目标后补齐队列并结束。

## 中断恢复与旧候选

保存任务模式、有效条件、账号ID、最后搜索位置和待采集字段。登录验证请用户处理，其他失败有限重试，避免不断刷新同一页面。

用户已将任务改为初筛，旧版仅因价格带、销量、无商单样本或未完成终审核实而排除的账号，可重新初看并纳入基本匹配队列；不是为了数量把严重不符者恢复。品牌明确否定者仍尊重其具体原因。

新项目不能直接复用旧报价/画像/商单为新数据。旧线索可快速定位，资料保留实际采集日期；未重新读取的写历史数据，不把旧图装成新图。恢复时先确认账号身份和页面状态。
